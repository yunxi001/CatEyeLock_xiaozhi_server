# 本地预览功能 - 方案对比总结

## 两种实现方案对比

### 方案 A：服务器端插件 ❌ 不推荐

**实现方式**：

```
用户语音 → ASR → LLM(服务器插件) → WebSocket命令 → ESP32
```

**优点**：

- ✅ 服务器端统一管理
- ✅ 可以添加复杂的业务逻辑

**缺点**：

- ❌ 需要在 `config.yaml` 中配置
- ❌ 如果使用 manager-api，还要在 Web 界面配置
- ❌ 每次新增设备功能都要修改服务器代码
- ❌ 服务器和设备职责不清晰
- ❌ 部署复杂，需要重启服务器
- ❌ 本质上只是一个"命令转发器"，没有实际业务逻辑

**实施成本**：

- 服务器端：3 个文件（插件、处理器、消息类型）
- 配置文件：1 处修改
- ESP32 端：1 个消息处理函数
- **总计**：约 400 行代码

---

### 方案 B：ESP32 端 MCP 工具 ✅ 强烈推荐

**实现方式**：

```
用户语音 → ASR → LLM(MCP工具) → 直接调用ESP32的MCP工具
```

**优点**：

- ✅ **零配置**：ESP32 连接时自动注册工具
- ✅ **自动发现**：LLM 自动识别新工具
- ✅ **架构清晰**：设备功能由设备实现
- ✅ **易扩展**：新增功能只需修改 ESP32
- ✅ **易维护**：逻辑集中在设备端
- ✅ **易部署**：只需更新 ESP32 固件

**缺点**：

- ⚠️ 需要修改 ESP32 固件（但这是合理的）

**实施成本**：

- 服务器端：**0 行代码**（无需修改）
- ESP32 端：1 个 MCP 工具定义 + 1 个处理函数
- **总计**：约 150 行代码

---

## 为什么 MCP 方案更好？

### 1. 符合架构设计原则

**单一职责原则**：

- 服务器：负责 AI 推理、语音处理、外部 API 调用
- ESP32：负责硬件控制、传感器读取、本地功能

**本地预览是设备本地功能，应该由设备实现。**

### 2. MCP 的设计初衷

MCP（Model Context Protocol）就是为了让 AI 能够**发现和调用设备端的工具**而设计的。

从现有的 5 个 MCP 工具可以看出：

- `self.get_device_status` - 设备状态查询
- `self.audio_speaker.set_volume` - 音量控制
- `self.screen.set_brightness` - 屏幕亮度
- `self.screen.set_theme` - 屏幕主题
- `self.camera.take_photo` - 拍照

**这些都是设备本地功能，都用 MCP 实现。本地预览也应该如此。**

### 3. 零配置的优势

**服务器端插件方案**：

```yaml
# 需要在 config.yaml 中配置
Intent:
  function_call:
    functions:
      - control_local_preview # 手动添加
```

**MCP 工具方案**：

```
# 无需任何配置！
# ESP32 连接时自动注册
# LLM 自动识别
```

### 4. 扩展性对比

**场景**：新增"屏幕旋转"功能

**服务器端插件方案**：

1. 创建 `control_screen_rotation.py`（服务器端）
2. 创建 `screenRotationHandler.py`（服务器端）
3. 修改 `textMessageType.py`（服务器端）
4. 修改 `textMessageHandlerRegistry.py`（服务器端）
5. 修改 `config.yaml`（服务器端）
6. 实现 ESP32 端处理函数
7. 重启服务器

**MCP 工具方案**：

1. 在 ESP32 添加 `self.screen.set_rotation` 工具
2. 实现处理函数
3. 上传固件

**差异**：MCP 方案只需修改 ESP32，无需动服务器！
