## 一、升级概述

本文档说明从 v5.0 升级到 v5.2 的所有变更，包括新增功能、字段变更和废弃内容。

### 版本对比

| 版本 | 发布日期 | 主要变更 |
|------|----------|----------|
| v5.0 | 2024-12-11 | 整合协议，与 App 协议对齐 |
| v5.1 | 2025-01-15 | 两级确认机制、统一错误码 |
| v5.2 | 2026-01-17 | seq_id 规范化、log_report 增强、新增事件类型 |

## 二、核心变更

### 2.1 两级确认机制【v5.1 新增】

**变更说明**：ESP32 收到命令后实现两级确认，提高可靠性。

**v5.0（旧版）**：
```json
// 只有一级确认
{
    "type": "ack",
    "msg_id": "cmd_1001",
    "code": 0,
    "msg": "OK"
}
```

**v5.2（新版）**：
```json
// 第一级：命令已收到
{
    "type": "esp32_ack",
    "seq_id": "1702234567890_0",
    "code": 0,
    "msg": "received"
}

// 第二级：命令执行完成
{
    "type": "ack",
    "seq_id": "1702234567890_0",
    "code": 0,
    "msg": "OK"
}
```

**影响**：
- ✅ Server 可以更快知道命令是否被 ESP32 接收
- ✅ 支持命令下发重试机制（等待 esp32_ack）
- ✅ 区分"接收失败"和"执行失败"

### 2.2 seq_id 替代 msg_id【v5.2 更新】

**变更说明**：统一使用 `seq_id` 字段名，与 App 协议对齐。

**v5.0（旧版）**：
```json
{
    "type": "lock_control",
    "msg_id": "cmd_1001",  // ❌ 旧字段名
    "command": "unlock"
}
```

**v5.2（新版）**：
```json
{
    "type": "lock_control",
    "seq_id": "1702234567890_0",  // ✅ 新字段名
    "command": "unlock"
}
```

**兼容性**：
- ✅ Server 端兼容旧版 `msg_id`（ackHandler 中实现）
- ✅ ESP32 端优先使用 `seq_id`，回退到 `msg_id`
- ⚠️ 建议所有新代码使用 `seq_id`

**seq_id 格式规范**：
- 格式：`时间戳_序号`（如 `1702234567890_0`）
- 生成方：App 端
- 传递规则：Server 透传，ESP32 保持不变

### 2.3 统一错误码【v5.1 更新】

**变更说明**：错误码从 7 个扩展到 10 个，覆盖更多场景。

**v5.0（旧版）**：
| code | 含义 |
|------|------|
| 0 | 成功 |
| 1 | 设备忙碌 |
| 2 | 参数错误 |
| 3 | 硬件故障 |
| 4 | 超时 |
| 5 | 未授权 |
| 6 | 资源不足 |
| 7 | 不支持 |

**v5.2（新版）**：
| code | 含义 | 说明 |
|------|------|------|
| 0 | 成功 | 操作成功完成 |
| 1 | 设备离线 | ESP32 未连接服务器 |
| 2 | 设备忙 | 正在执行其他操作 |
| 3 | 参数错误 | 命令格式或参数无效 |
| 4 | 不支持 | 不支持的命令或操作 |
| 5 | 超时 | 等待响应超时 |
| 6 | 硬件故障 | 硬件异常或不可用 |
| 7 | 资源已满 | 指纹/NFC 存储已满 |
| 8 | 未认证 | 用户未登录或权限不足 |
| 9 | 重复消息 | seq_id 重复（防重放） |
| 10 | 内部错误 | 未知内部异常 |

**映射关系**：
- v5.0 code 1 → v5.2 code 2（设备忙）
- v5.0 code 5 → v5.2 code 8（未认证）
- v5.0 code 6 → v5.2 code 7（资源已满）
- v5.0 code 7 → v5.2 code 4（不支持）
- 新增 code 1（设备离线）
- 新增 code 9（重复消息）
- 新增 code 10（内部错误）

## 三、消息格式变更

### 3.1 log_report 增强【v5.2 更新】

**变更说明**：新增 `status` 和 `lock_time` 字段，支持设备锁定状态。

**v5.0（旧版）**：
```json
{
    "type": "log_report",
    "ts": 1702234567890,
    "data": {
        "method": "finger",
        "uid": 5,
        "result": true,  // ❌ 只有成功/失败
        "fail_count": 0
    }
}
```

**v5.2（新版）**：
```json
{
    "type": "log_report",
    "ts": 1702234567890,
    "data": {
        "method": "finger",
        "uid": 5,
        "status": "success",  // ✅ 新增：success/fail/locked
        "lock_time": 0,       // ✅ 新增：剩余锁定时间（分钟）
        "fail_count": 0
    }
}
```

**status 取值**：
| status | 说明 | lock_time |
|--------|------|-----------|
| `success` | 开锁成功 | 0 |
| `fail` | 开锁失败 | 0 |
| `locked` | 设备已锁定 | > 0（剩余锁定时间，分钟） |

**兼容性**：
- ✅ Server 端兼容旧版 `result` 字段
- ✅ 自动转换：`result: true` → `status: "success"`
- ✅ 自动转换：`result: false` → `status: "fail"`

### 3.2 event_report 新增事件类型【v5.2 更新】

**变更说明**：新增 3 个事件类型，支持更多场景。

**v5.0（旧版）**：
| event | 说明 |
|-------|------|
| `bell` | 门铃按下 |
| `pir_trigger` | PIR 人体检测 |
| `tamper` | 撬锁报警 |
| `door_open` | 门未关超时 |
| `low_battery` | 低电量警告 |

**v5.2（新版）**：
| event | 说明 | v5.2 新增 |
|-------|------|-----------|
| `bell` | 门铃按下 | |
| `pir_trigger` | PIR 人体检测 | |
| `tamper` | 撬锁报警 | |
| `door_open` | 门未关超时 | |
| `low_battery` | 低电量警告 | |
| `door_closed` | 门已关闭 | ✅ |
| `lock_success` | 上锁成功 | ✅ |
| `bolt_alarm` | 反锁报警 | ✅ |

**新增事件说明**：
- `door_closed`：门磁检测到门已关闭
- `lock_success`：锁舌成功伸出（上锁完成）
- `bolt_alarm`：反锁状态下尝试开锁触发报警

### 3.3 face_result 规范化【v5.2 更新】

**变更说明**：明确 face_result 是主动上报，不携带 seq_id。

**v5.0（旧版）**：
```json
{
    "type": "face_result",
    "msg_id": "face_001",  // ❌ 错误：不应该携带
    "result": "known",
    "user_id": 5,
    "access": {...}
}
```

**v5.2（新版）**：
```json
{
    "type": "face_result",
    // ✅ 不携带 seq_id（主动上报）
    "result": "known",
    "user_id": 5,
    "access": {...}
}
```

**说明**：
- face_result 是响应 ESP32 主动请求，不是命令响应
- 工作流程：ESP32 检测到人脸 → Server 返回 face_result → ESP32 上报 log_report
- 整个流程都不需要 seq_id

## 四、数据库表结构变更

### 4.1 unlock_logs 表更新【v5.2 更新】

**变更说明**：新增 `status` 和 `lock_time` 字段。

**v5.0（旧版）**：
```sql
CREATE TABLE unlock_logs (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    device_id VARCHAR(64),
    method VARCHAR(16),
    user_id INT,
    result TINYINT,  -- 0=失败, 1=成功
    fail_count INT,
    created_at DATETIME
);
```

**v5.2（新版）**：
```sql
CREATE TABLE unlock_logs (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    device_id VARCHAR(64),
    method VARCHAR(16),
    user_id INT,
    status VARCHAR(16),  -- success/fail/locked
    lock_time INT,       -- 剩余锁定时间（分钟）
    fail_count INT,
    created_at DATETIME
);
```

**迁移 SQL**：
```sql
-- 添加新字段
ALTER TABLE unlock_logs 
ADD COLUMN status VARCHAR(16) AFTER user_id,
ADD COLUMN lock_time INT DEFAULT 0 AFTER status;

-- 迁移旧数据
UPDATE unlock_logs 
SET status = CASE 
    WHEN result = 1 THEN 'success'
    WHEN result = 0 THEN 'fail'
    ELSE 'fail'
END
WHERE status IS NULL;

-- 可选：删除旧字段（建议保留一段时间）
-- ALTER TABLE unlock_logs DROP COLUMN result;
```

## 八、常见问题

### Q1: 升级后旧版 ESP32 还能用吗？

**A**: 可以。v5.2 Server 完全兼容 v5.0 ESP32：
- 自动将 `msg_id` 转换为 `seq_id`
- 自动将 `result` 转换为 `status`
- 不影响现有功能

### Q2: 必须同时升级 Server 和 ESP32 吗？

**A**: 不需要。建议先升级 Server，再逐步升级 ESP32：
- Server 升级后立即获得新功能（如重试机制）
- ESP32 可以按设备逐步升级
- 不会影响线上服务

### Q3: 数据库迁移会丢失数据吗？

**A**: 不会。迁移脚本只是添加新字段和转换数据：
- 保留所有旧数据
- 自动转换 `result` 为 `status`
- 建议先在测试环境验证

### Q4: seq_id 和 msg_id 有什么区别？

**A**: 只是字段名不同，功能相同：
- `seq_id` 是新版字段名，与 App 协议对齐
- `msg_id` 是旧版字段名，仍然兼容
- 推荐新代码使用 `seq_id`

### Q5: 为什么需要两级确认？

**A**: 提高可靠性和用户体验：
- 第一级（esp32_ack）：快速反馈命令是否被接收
- 第二级（ack）：反馈命令是否执行成功
- 支持命令下发重试机制
