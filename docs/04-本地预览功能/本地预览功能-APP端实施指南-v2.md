## 1. 功能概述

### 1.1 目标

实现 APP 端对 ESP32 本地预览功能的远程控制，允许用户通过手机 APP 启动/停止 ESP32 的本地预览功能。

### 1.2 用户场景

**场景1：远程启动本地预览**

```
用户在 APP 中点击"打开本地预览"按钮
→ APP 发送控制消息
→ 服务器转发命令到 ESP32
→ ESP32 启动本地预览
→ APP 显示"已打开本地预览"
```

**场景2：远程停止本地预览**

```
用户在 APP 中点击"关闭本地预览"按钮
→ APP 发送控制消息
→ 服务器转发命令到 ESP32
→ ESP32 停止本地预览
→ APP 显示"已关闭本地预览"
```

## 2. 实施方案对比

### 方案A：通过 WebSocket 消息控制（推荐，可立即实施）

**优点**：

- ✅ 无需服务器端额外开发
- ✅ 可立即实施
- ✅ 实时性高

**缺点**：

- ❌ 需要维护 WebSocket 连接
- ❌ 需要自己处理响应等待

**实施方式**：

- APP 通过 WebSocket 发送 `{"type": "forward", "target": "esp32", "data": {"type": "local_preview", "action": "start"}}` 消息
- 服务器转发到 ESP32
- ESP32 返回响应
- 服务器转发响应到 APP

### 方案B：通过 HTTP API 控制（需要服务器端先实现）

**优点**：

- ✅ 实现简单
- ✅ 无需维护长连接
- ✅ 标准 RESTful API

**缺点**：

- ❌ 需要服务器端先实现 HTTP API 接口
- ❌ 实时性略低

**实施方式**：

- APP 调用 HTTP API：`POST /api/device/{device_id}/local_preview`
- 服务器处理请求并转发到 ESP32
- 服务器返回结果给 APP

**当前状态**：❌ 服务器端未实现，需要先开发

## 3. 方案A：WebSocket 消息控制（推荐）

### 3.1 需要实现的功能

#### 3.1.1 用户界面（UI）

**控制按钮**：

- 位置：设备控制页面
- 与"监控模式"按钮并列显示

**按钮状态**：

- 未启动：显示"打开本地预览"，灰色
- 运行中：显示"关闭本地预览"，高亮色
- 禁用：显示"本地预览（不可用）"，浅灰色

**交互设计**：

- 点击按钮 → 显示加载动画
- 禁用按钮，防止重复点击
- 收到响应后更新按钮状态
- 显示操作结果提示

#### 3.1.2 WebSocket 消息发送

**发送控制命令**：

启动本地预览：

```json
{
  "type": "forward",
  "target": "esp32",
  "data": {
    "type": "local_preview",
    "action": "start"
  }
}
```

停止本地预览：

```json
{
  "type": "forward",
  "target": "esp32",
  "data": {
    "type": "local_preview",
    "action": "stop"
  }
}
```

**说明**：

- `type: "forward"` 表示转发消息
- `target: "esp32"` 表示转发到 ESP32
- `data` 是实际的控制命令

#### 3.1.3 响应处理

**ESP32 响应格式**（通过服务器转发）：

成功响应：

```json
{
  "type": "forward",
  "source": "esp32",
  "data": {
    "type": "local_preview",
    "action": "start",
    "status": "success"
  }
}
```

失败响应：

```json
{
  "type": "forward",
  "source": "esp32",
  "data": {
    "type": "local_preview",
    "action": "start",
    "status": "error",
    "error": "Monitor mode active"
  }
}
```

**需要处理的逻辑**：

- 监听 WebSocket 消息
- 识别 `type: "forward"` 且 `source: "esp32"` 的消息
- 提取 `data.type: "local_preview"` 的响应
- 根据 `status` 更新 UI

#### 3.1.4 错误处理

**错误码映射**：

| ESP32 错误信息            | 用户提示                             |
| ------------------------- | ------------------------------------ |
| `Camera not available`    | "摄像头暂时不可用"                   |
| `Monitor mode active`     | "监控模式正在运行，请先关闭监控模式" |
| `Face recognition active` | "人脸识别正在进行，请稍后再试"       |
| `System error`            | "系统错误，请稍后再试"               |
| 超时（10秒无响应）        | "操作超时，请稍后再试"               |

### 3.3 技术要点

#### 3.3.1 响应等待机制

**问题**：如何知道哪个响应对应哪个请求？

**解决方案**：

- 方案1：使用请求 ID（需要服务器端支持）
- 方案2：基于时间窗口匹配（发送请求后 10 秒内的响应）
- 方案3：基于消息类型匹配（假设同一时间只有一个请求）

**推荐**：方案3（最简单，适合当前场景）

#### 3.3.2 超时处理

**实现逻辑**：

- 发送请求后启动 10 秒定时器
- 收到响应后取消定时器
- 定时器到期后显示"操作超时"

#### 3.3.3 状态同步

**实时同步方式**：

- 监听 WebSocket 消息
- 识别状态变化消息
- 更新本地状态
- 刷新 UI

**同步场景**：

- 其他用户通过 APP 改变状态
- 用户通过语音命令改变状态
- ESP32 自动停止

### 3.4 互斥逻辑

**与监控模式互斥**：

**方案1：APP 端预检查（推荐）**

- APP 维护监控模式和本地预览的状态
- 发送请求前检查状态
- 如果冲突，直接显示提示，不发送请求

**方案2：依赖服务器端检查**

- APP 直接发送请求
- 服务器或 ESP32 返回错误
- APP 根据错误码显示提示

**推荐**：方案1（提升用户体验，减少无效请求）

## 4. 方案B：HTTP API 控制（需要服务器端先实现）

### 4.1 服务器端需要实现的接口

#### 4.1.1 启动本地预览

**接口定义**：

- 请求方法：POST
- 请求路径：`/api/device/{device_id}/local_preview`
- 请求头：`Authorization: Bearer {token}`
- 请求体：`{"action": "start"}`

**成功响应**：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "status": "running"
  }
}
```

**失败响应**：

```json
{
  "code": 1001,
  "message": "Monitor mode is active",
  "data": null
}
```

#### 4.1.2 停止本地预览

**接口定义**：

- 请求方法：POST
- 请求路径：`/api/device/{device_id}/local_preview`
- 请求头：`Authorization: Bearer {token}`
- 请求体：`{"action": "stop"}`

**响应格式**：同上

#### 4.1.3 查询状态（可选）

**接口定义**：

- 请求方法：GET
- 请求路径：`/api/device/{device_id}/local_preview/status`
- 请求头：`Authorization: Bearer {token}`

**成功响应**：

```json
{
  "code": 0,
  "message": "success",
  "data": {
    "local_preview_active": true,
    "start_time": "2026-05-04T10:30:00Z"
  }
}
```

### 4.2 APP 端实施步骤

**前提条件**：服务器端已实现上述 HTTP API 接口

**实施步骤**：

1. 封装 HTTP API 调用方法
2. 实现请求超时处理
3. 实现错误码解析
4. 实现响应数据解析
5. 连接到 UI 组件

**预计时间**：约 8 小时（比方案A简单）
